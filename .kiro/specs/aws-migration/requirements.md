# 要件定義書: AWS 移行

## はじめに

フロントエンド（Vercel）とバックエンド（Render）を AWS に移す。DB は Supabase のまま。
本 Spec は移行作業の間だけ使い、移行完了後に削除する。恒久的に残す情報（構成・運用手順・コスト方針）は移行作業の中で steering と各 Spec に移す（要件10）。

**目的:** 商用リリースまで費用をかけずに運用し、そのまま商用の構成に移れるようにする。Render の無料プランは本番利用が想定されておらず、15分の無通信で停止し、外部への大量通信で停止されることがある。Vercel の無料プランは広告などの商用利用ができない。

## 用語集

- **Frontend**: Next.js のフロントエンド
- **API**: FastAPI のバックエンド
- **Backfill_Worker**: 応答後に過去の試合を取得する処理（現在は API 内の BackgroundTasks）
- **Always_Free**: AWS の期限のない無料枠（毎月リセット）
- **許可ユーザー**: アプリの利用を許可したユーザー（メールアドレスで指定）

## 要件

### 要件1: フロントエンドの配信

**ユーザーストーリー:** 運営者として、フロントエンドを費用をかけずに配信したい。そうすることで、Vercel の無料プランの制約（商用利用不可）から外れられる。

#### 受け入れ基準

1. Frontend は静的ファイルとして書き出し、CloudFront 経由で配信する。配信元のストレージは公開しない
2. Frontend の全画面（サモナー検索、チャンピオン検索・ビルド、ノート）は移行前と同じ機能・表示で動く
3. Frontend はサーバーで動く処理を持たない（ログインのコールバックを含め、ブラウザ側で処理する）
4. WHEN 存在しない URL にアクセスした場合、Frontend は Not Found 画面を表示する
5. ページの URL（`/champion/{チャンピオン}` など）は移行前と同じとする

### 要件2: バックエンドの実行

**ユーザーストーリー:** 運営者として、API を停止せずに費用をかけず動かしたい。そうすることで、初回アクセスの待ち時間（約1分）をなくせる。

#### 受け入れ基準

1. API はサーバーレスの関数として動き、既存のエンドポイントとレスポンスを変えない
2. API は使われていない間に料金が発生しない
3. Backfill_Worker は API の応答とは別に起動し、応答の速さに影響しない
4. API と Backfill_Worker は同じ取り込み処理（試合の保存・補完・カーソル更新）を使い、移行前と同じ結果になる
5. WHEN Backfill_Worker が処理の上限時間に近づいた場合、Backfill_Worker はそこまでの結果を保存して終了し、次回に続きから取得する

### 要件3: Riot API のレート制限

#### 受け入れ基準

1. API と Backfill_Worker（将来のクローラーを含む）は同じ API キーを使うため、各処理に割り当てる上限の合計がキーの上限を超えないように設定できる
2. 同じ処理が同時に複数動いて上限を超えないよう、各処理の同時実行数を制限できる
3. 上限値の切り替え（Production キーへの切り替え時）は設定の変更だけで行える

### 要件4: 試合の生データの保管

#### 受け入れ基準

1. 試合の生データ（詳細・タイムライン）は AWS の非公開ストレージに保管する
2. Supabase Storage に保管済みの生データは AWS のストレージに移し、移行後に削除する
3. 生データの保存先の切り替えは adapters 層だけで行い、services 層を変更しない

### 要件5: アクセスの制限

**ユーザーストーリー:** 運営者として、Production キーを取得するまでサイトを自分（と審査担当者）だけが使える状態にしたい。そうすることで、Personal キーの規約（一般公開の禁止）を守れる。

制限は2段階とし、どちらか一方が破られても他方で守る。

#### 受け入れ基準

**第1段階: サイトへの入口（CloudFront）**

1. CloudFront は、許可した IP アドレスからのアクセスを受け付ける
2. CloudFront は、ベーシック認証で正しいユーザー名とパスワードを入力したアクセスを受け付ける（Production キーの審査用）
3. IF 1・2 のどちらにも当てはまらない場合、CloudFront はアクセスを拒否する
4. 画面と API の入口は CloudFront だけとし、API を CloudFront を経由せずに呼べないようにする

**第2段階: 利用者（API）**

5. API は、許可したメールアドレスの利用者のログイン情報を持たないリクエストを 401 で拒否する（ログインが不要な画面の API を含む）
6. Frontend は、ログインしていない利用者にログイン画面だけを表示する。許可していないメールアドレスでログインした場合は、利用できないことを表示する

**設定**

7. 許可する IP アドレス・ベーシック認証の資格情報・許可するメールアドレス・各段階の有効／無効は、コードを変更せずに変更できる
8. 審査期間中は第2段階を無効にでき、審査後に元に戻せる（審査担当者のメールアドレスは事前に分からないため）
9. Production キー取得後の一般公開時は、両方の段階をコード変更なしで解除できる
10. Google ログインによる利用者ごとのデータの分離（ノート・お気に入り）は、制限の有無に関係なく維持する

### 要件6: 秘密情報

#### 受け入れ基準

1. Riot API キー・Supabase の secret キーは暗号化して AWS に保管し、コード・リポジトリ・ログ・関数の環境変数に平文で置かない
2. 各関数は自分に必要な秘密情報だけを読める

### 要件7: 構成管理とデプロイ

**ユーザーストーリー:** 運営者として、構成をコードで管理し、プッシュで自動デプロイしたい。そうすることで、手作業の設定ミスを防げる。

#### 受け入れ基準

1. AWS のリソースはすべて CloudFormation で定義し、手作業で作らない（初回の準備を除く）
2. WHEN `main` に変更が入った場合、テストが通った後にフロントエンドとバックエンドが自動でデプロイされる
3. デプロイは長期間有効なアクセスキーを使わずに行う
4. デプロイに失敗した場合、動いている環境は以前の状態のまま残る

### 要件8: セキュリティ

#### 受け入れ基準

1. 各リソースの権限は必要最小限とする
2. 外部から直接呼べる入口は CloudFront だけとする。API と Backfill_Worker は外部から直接呼べない
3. 通信はすべて HTTPS とする
4. 運営者の AWS アカウントは多要素認証で保護し、日常の作業にルートユーザーを使わない

### 要件9: コスト

#### 受け入れ基準

1. 自分1人の利用と Backfill の想定量で、AWS の月額は Always_Free の範囲（0円）に収める
2. 月額が設定額（初期値 $1）を超えそうな場合、運営者にメールで通知する
3. 固定費が発生する構成（NAT Gateway、常時起動のサーバー、Provisioned Concurrency など）は使わない
4. ログは保存期間を設定し、無期限に溜めない

### 要件10: 切り替えと後片付け

#### 受け入れ基準

1. 新しい環境で全機能を確認してから、利用者が使う URL を新しい環境に切り替える
2. 切り替え後、問題がないことを確認してから Vercel と Render のサービスを停止する
3. steering（tech.md、structure.md）と各 Spec の Vercel・Render に関する記述を、AWS の構成に書き換える
4. 移行完了後も必要な情報は次の場所に移してから、本 Spec を削除する
   - `docs/architecture.md`（人向け）: システム全体の構成図、CI/CD の構成図（Mermaid）、デプロイ手順、秘密情報・アクセス制限の設定手順、コスト方針
   - `.kiro/steering/tech.md`（AI 向け）: 技術構成と制約の要点と、`docs/architecture.md` への参照
   - CloudFormation のテンプレート: AWS のリソース構成の正

### 要件11: 範囲外

- DB の移行（Supabase のまま）
- クローラー（別 Spec。本 Spec の構成の上で作る）
- 独自ドメイン、SEO、広告（一般公開時に別途対応）
