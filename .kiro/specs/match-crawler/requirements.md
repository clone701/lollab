# 要件定義書: 試合の自動収集（クローラー）

## はじめに

チャンピオンビルドの統計は、今はサモナー検索・更新・Backfill で集まった試合だけから作っている。自分が検索した相手の試合に偏り、試合数も少ない。
定期的に JP サーバーの高ランク帯のソロランクの試合を集め、統計の試合数を増やし、ランク帯で絞り込めるようにする。

費用は AWS の無料枠と Supabase の無料プランの範囲に収め、Riot API の利用は Personal キーの上限内で、検索の操作を妨げない量にする。

## 用語集

- **クローラー**: 定期的に起動し、試合を集めて保存する処理
- **収集元プレイヤー**: 試合を取る元にするプレイヤー。ランクの一覧から選ぶ
- **対象ランク帯**: エメラルド・ダイヤモンド・マスター・グランドマスター・チャレンジャー
- **試合のランク帯**: その試合を取った収集元プレイヤーのランク帯（参加者10人全員のランクは取得しない）
- **検索由来の試合**: サモナー検索・更新・Backfill で保存した試合
- **生データ**: Riot API から取得した試合詳細とタイムラインの JSON

---

## 要件

### 要件1: 定期的な収集

**ユーザーストーリー:** 運営者として、操作しなくても統計用の試合が増えてほしい。そうすることで、統計の信頼性が上がる。

#### 受け入れ基準

1. クローラーは30分ごとに自動で起動する
2. クローラーは JP サーバーのソロランク（ソロ/デュオ）の試合だけを集める
3. クローラーは対象ランク帯の収集元プレイヤーの直近の試合を集める
4. クローラーは試合詳細とタイムラインの両方を保存し、検索由来の試合と同じ形式で統計に使えるようにする
5. クローラーは保存済みの試合を取り直さない
6. クローラーは同じ収集元プレイヤーばかりに偏らないよう、収集元プレイヤーを順に入れ替える
7. クローラーは1日あたり2,000試合以上を集める（Riot API の上限内で集められる量の目安）
8. WHILE 前回の起動の処理が続いている間、クローラーは新しい起動で処理を重ねて行わない

### 要件2: ランク帯の記録

**ユーザーストーリー:** プレイヤーとして、自分のランク帯に近い試合の統計を見たい。そうすることで、自分に合ったビルドを選べる。

#### 受け入れ基準

1. クローラーは集めた試合ごとに試合のランク帯を記録する
2. 同じ試合が複数の収集元プレイヤーから見つかった場合、最初に記録したランク帯を保つ
3. 検索由来の試合はランク帯を持たない（ランク帯の絞り込みでは「すべて」にだけ含める）
4. ランク帯による絞り込みの表示は champion-stats Spec で扱う

### 要件3: Riot API の利用量

**ユーザーストーリー:** 運営者として、クローラーが動いていても検索がこれまでどおり使えてほしい。そうすることで、自分の操作が妨げられない。

#### 受け入れ基準

1. クローラーの Riot API の利用量は、検索・更新・Backfill の分と合わせて、キーの上限を超えない
2. クローラーの利用量の上限は、コードを変えずに設定だけで変えられる（Production キーへの切り替えに備える）
3. IF Riot API がレート制限（429）を返した場合、クローラーはその回の処理を終え、次の起動で続きから行う
4. IF Riot API が一時的なエラー（5xx・タイムアウト）を返した場合、クローラーはその試合を飛ばして処理を続ける
5. IF 一度の起動で失敗が続く場合、クローラーはその回の処理を早めに終える

### 要件4: 保存量の上限

**ユーザーストーリー:** 運営者として、保存量が無料プランの上限を超えないでほしい。そうすることで、費用が発生しない。

#### 受け入れ基準

1. DB に保存する試合は、検索由来の試合を除いて直近10万試合までとする
2. WHEN 試合数が上限を超えた場合、システムはゲーム終了日時が古い試合から削除する
3. 検索由来の試合と、検索済みのサモナーが参加した試合は、上限による削除の対象にしない（サモナーの試合履歴を失わない）
4. 生データは S3 に保存し、1回の起動で集めた分をまとめて保存する（ファイル数とリクエストの料金を抑える）
5. 生データの保存先と形式が変わっても、既存の生データを読めること

### 要件5: 費用

#### 受け入れ基準

1. クローラーの実行にかかる AWS の料金は、他の機能と合わせて無料枠の範囲に収まる
2. クローラーは常時起動のサーバーを使わない

### 要件6: 運用

**ユーザーストーリー:** 運営者として、クローラーの状態を把握し、必要なら止めたい。そうすることで、問題が起きても対処できる。

#### 受け入れ基準

1. クローラーは起動ごとに、集めた試合数・飛ばした試合数・終了理由をログに残す
2. クローラーはコードを変えずに設定だけで停止・再開できる
3. ログには API キーなどの秘密情報を含めない

### 要件7: 範囲外

- JP 以外のサーバー、フレックス・ノーマル・ARAM の収集
- 参加者10人全員のランクの取得（1試合あたりの API 呼び出しが大きく増えるため）
- 集計結果を保存するテーブル（集計が遅くなったら champion-stats Spec で扱う）
- ティアリスト・カウンター（別 Spec）
